Version Checker 2.0 — rewrite plan

A small, fast plugin that underlines outdated versions, removes redundant Maven overrides, and updates a file or the whole project by patch, minor or major. Maven and npm come first. Gradle support is basic. Drafted 2026-10-31 from the code at d5758d0.

The idea in one paragraph. The current plugin asks each build tool for versions: it starts a Maven JVM with a helper JAR, runs npm view / pnpm view / yarn info / bun info, and runs a Gradle init-script task. Around that it has a large layer of leases, previews, coverage tracking and edit authorization. Version 2 reads repository metadata over HTTP from one shared client, caches it aggressively, and shows results with an ExternalAnnotator. Updates are plain PSI edits in one undoable command.
  • Keep: outdated-version warnings with patch, minor and major quick fixes; the Maven redundant-override inspection; the minimum release age (quarantine); the Maven and Gradle wrappers.
  • Add: six actions: Update This File and Update All Files, each for Patch, Minor or Major.
  • Drop: the Review dialog, status widget, shared policy file, ignore and deprecation lists, follow-up notifications, the Maven helper process, the Node CLI, the pnpm, Yarn and Bun adapters, and the Gradle init script.

1 · What the plugin does

Outdated version warnings

A wavy underline on the version text, in pom.xml, package.json, build.gradle(.kts), libs.versions.toml and the wrapper properties.

Example message: “junit:junit 4.12 → 4.13.2 (minor) · 5.0.0 (major)”.

Alt+Enter offers up to three fixes: Update to 4.12.1 (patch), Update to 4.13.2 (minor) and Update to 5.0.0 (major). If two kinds point to the same version, it shows one fix.

Severity defaults to Warning. You can change it to Error in Settings → Editor → Inspections, as with any inspection.

Redundant Maven overrides

An offline weak warning, which needs no network:

  • A <property> with the same value as the parent's.
  • A <version> equal to the version from dependencyManagement, a parent or a BOM.
  • An older override when the parent gives a newer version.
  • optional A version property that nothing uses in this POM or its child modules in the project.

Fix: Remove redundant override, plus Remove all in file.

Update a file or every file

Tools → Versions, the editor context menu and the Project view context menu:

  • Update This File ▸ Patch / Minor / Major
  • Update All Files ▸ Patch / Minor / Major

Each mode picks the newest version in its branch. Patch finds the newest 1.2.x even when 2.0 exists. All edits apply as one undoable command. A notification reports “Updated 14 versions in 3 files”.

Quarantine (minimum release age)

One setting, Minimum release age (hours). Releases newer than this are hidden from warnings, quick fixes and bulk updates.

New: it now covers Gradle libraries and plugins too, because version 2 reads the same Maven metadata directly. In version 1 the Gradle task could not supply release times.

optional Read the package manager's own setting when one exists, and use the larger value. See §5.

4 · How it stays fast

The goal: an open file shows hints in under 300 ms when the cache is warm, and about one network round trip when it is cold. Checking the whole project should be limited by parallel HTTP only, with no processes and no build-tool startup.

1 · CollectRead action. Find declarations in the PSI or text. No I/O.
2 · Memory cacheFresh result → annotate now. Stale → annotate now and revalidate in the background.
3 · CoalesceOne in-flight request per (repo, coordinate), shared by all files and modules.
4 · Parallel HTTPOne java.net.http client over HTTP/2 with keep-alive. 8–16 parallel requests per host.
5 · Conditional GETIf-None-Match / If-Modified-Since. A 304 returns no body.
6 · Annotateapply() on the EDT. Fixes are computed already.

Caches

  • Version lists: in memory, fresh for 30 min, then served stale while revalidating. ETags persist on disk, so a restart costs one 304 per coordinate.
  • Release times: they never change, so cache them on disk with no expiry, keyed by repo + coordinate + version. After the first check, the quarantine costs nothing.
  • “Check Now” clears the in-memory cache. Release times stay.

Less data per request

  • Maven: maven-metadata.xml only, usually a few KB. POM HEAD requests run only when the quarantine needs them.
  • npm: the abbreviated packument (Accept: application/vnd.npm.install-v1+json) when the quarantine is 0. The full document only when release times are needed.
  • Repositories: query all effective repositories in parallel and merge the results. With a * mirror that is one request.

To measure, Phase 0 records the time for your real work projects to show hints in an open file and to check the whole project, with the current plugin. Phase 4 checks the new plugin against those numbers. This plan does not guess them.

5 · Quarantine, by ecosystem

EcosystemRelease time fromShortcut
Maven, Gradle libraries and plugins, Maven wrapperThe Last-Modified header of a HEAD request on the version's .pomIf <lastUpdated> in the metadata is older than the cutoff, every version is old enough, so no HEAD requests run. Otherwise HEAD newest-first inside each branch (patch, minor, major) and stop at the first version that is old enough. Requests run in parallel and the results are cached forever.
npmThe packument's time[version]One full-document request gives all the times.
Gradle wrapperbuildTime in services.gradle.org/versions/allOne request.

Selection rule (shared by all ecosystems):

candidates = stable(versions).filter { it > current && releasedAt(it) <= now - minAge }
patch = newest c with same major.minor
minor = newest c with same major
major = newest c

optional Read the package manager's own age gate and use the larger value. pnpm: minimumReleaseAge in pnpm-workspace.yaml. Yarn: npmMinimalAgeGate in .yarnrc.yml. Bun: minimumReleaseAge in bunfig.toml. Check each key name and unit against current docs before building this.

Why ExternalAnnotator

The platform built it for slow external lookups. collectInformation runs under a read lock, doAnnotate runs on a background thread and may block on the network, and apply adds the highlights. That replaces the custom queue, the result cache leases and the DaemonCodeAnalyzer.restart calls. A paired LocalInspectionTool that implements ExternalAnnotatorBatchInspection keeps the on/off switch and severity in Settings → Inspections, and keeps the results in Inspect Code.

Optional plugin dependencies

  • org.jetbrains.idea.maven → the Maven declarations, repositories and override inspection
  • com.intellij.modules.json → package.json (no JavaScript plugin needed)
  • org.toml.lang → the TOML catalog; the tomlj library goes
  • Gradle scripts are read as text, so the Kotlin and Groovy plugins are not needed
  • Properties files cover both wrappers

11 · Decisions for you

1 · Bulk update: preview or not?

Recommendation: no dialog. Apply in one command, then show a notification with Undo and a list of the changes. Option: a small checkbox list (about 120 lines) before applying to the whole project.

2 · Keep the wrapper checks?

Recommendation: yes. About 140 lines in total, and they reuse the Maven client. They are useful for plugin development, where the Gradle wrapper version matters.

3 · Drop “ignore this version”?

Recommendation: drop it in 2.0. The quarantine covers the main case, which is “too new to trust”. It is easy to add back later as one setting.

4 · Unused-property detection?

Recommendation: include it, limited to version-like property names that nothing references in the POM and its child modules in the project. Without that limit, false positives are likely.
