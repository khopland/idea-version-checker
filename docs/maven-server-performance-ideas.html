Version Checker / performance proposal / 10 October 2026

Make big Maven projects
feel small.

For Spring Boot children, large reactors, and POMs full of dependency management: reduce repeated model building and repository lookups, then make useful results arrive sooner.

Based on the current repository code. These are proposals, with implementation tradeoffs and experiments; no large-project speedup has been measured for them.

My strongest bet

Resolve each unique artifact once per repository context. Reuse it everywhere.

A hundred modules can reference the same libraries at different versions. Cache the available version list, share fresh lookups across the scan, and select patch/minor/major candidates for each declaration from that one list. Then evolve toward a small batched query running inside Maven.

Start with scan-wide freshness and session experiments. Build the metadata service if request counts or repeated goal work show that it will pay off.

01 / diagnosis

The BOM is only part of the story.

A Boot child with 25 dependencies

The adapter collects supported declarations from the selected POM, plus inherited consumers of properties overridden there. It sends exact group/artifact inclusion filters to the dependency goal.

It also sets processDependencyManagementTransitive=false. Imported BOM contents are already excluded from a blanket update report. Dependencies declared without a version can still be checked using their managed baseline.

The effective model still contains inheritance and management. A small query scope does not guarantee cheap model construction. The inclusion behavior is documented by MojoHaus.

A parent with 1,000 managed entries

If those entries are explicitly declared in the selected project POM and are supported, they belong to the snapshot. Existing filters faithfully retain them. Checking fewer would be a deliberate change in scope.

Across a reactor, the same coordinates can appear in many snapshots. Each POM currently gets a fresh embedder and its own goals, with metadata timestamps expired again before querying.

Likely pressure points: repeated setup, repeated refresh, plugin branch passes, and serialized checks. Their share of total latency needs a native large-project trace.

02 / proposals

Eight ways to cut the wait.

01First experiment · medium effort

Refresh once for the whole scan.

Give a whole-project refresh one generation. Track successful revalidation by artifact and effective repository context, so later modules do not expire the same metadata again.

Automatic checks can reuse verified metadata until its deadline. Explicit Refresh still requests fresh metadata, but fresh means once for that generation rather than once per POM.

Payoff: fewer duplicate network checks and tracking-file writes in overlapping modules.
Constraint: an “expired” flag alone is insufficient. Mark reuse only after a successful refresh; failed or cancelled work must remain retryable.
Concrete change

Pass a scan context into MavenVersionLookup and expireMetadata. Preserve repository/profile/authentication isolation and Maven file locking. The native Versions goal may still request metadata; verify actual HTTP savings with a counting repository.

02Highest potential · large effort

Share raw version metadata.

Introduce a Maven metadata service with bounded caching and shared in-flight requests. Store the stable version index, then compute candidates for each baseline and mode.

Changing 1.2.0 to 1.3.0, or switching a preview from Major to Patch, should not require another network lookup when the version index is still fresh.

Payoff: work scales with unique coordinates and contexts, rather than module declarations and modes.
Constraint: keep strict POM fingerprints for edits. Metadata reuse and permission to apply an edit have different lifetimes.
Cache rules worth getting right

Key by group/artifact, effective ordered repositories and policies, mirrors, auth/proxy digest, local repository, relevant Maven runtime/extensions/configuration, and refresh generation. Separate plugin repository contexts. Propagate the original metadata expiry into derived reports; deriving a report cannot extend freshness. Bound memory, isolate failures, and cancel workers when their last consumer leaves. The npm metadata cache in this repo is a useful lifecycle template.

03Profile first · medium effort

Keep Maven warm during a scan.

Replace one fresh embedder manager per POM with a short-lived scan session that leases compatible embedders. Reload unchanged settings once within that session.

Retain each module's effective model and repository context. Reuse a module model across its lookup phases where the native API permits it; sharing settings does not make different POM models interchangeable.

Payoff: less setup when MAVEN_SESSION, MAVEN_SETTINGS, or MAVEN_MODEL dominate.
Constraint: sequential use initially; release and reset on completion, cancellation, project disposal, or unload.
Compatibility boundary

Group only after comparing the Maven distribution, JDK, settings, local repo, profiles, ancestor .mvn inputs and extensions. A shared directory or parent coordinate is not sufficient. Measure acquisition/reset behavior rather than assuming every fresh wrapper starts a new JVM.

04Architecture option · large effort

Ask Maven one small question.

Prototype a read-only Maven helper goal that accepts explicit coordinate batches and returns structured results. Use Maven Resolver inside the configured Maven session for version metadata, without running a display-report goal per category or branch.

Return per-artifact results and errors. Publish batches as they finish. A single malformed version list should not force the whole dependency goal to run again.

Payoff: less repeated goal/model/report work, better failure isolation, and a natural home for the shared version index.
Constraint: retain native mirrors, credentials, proxies, profiles and version ordering. Plugin candidates also need Maven prerequisite checks.
Migration approach

Start with dependencies and external parents; retain the existing plugin path. Compare exact candidates against Versions Plugin 2.21.0 in controlled tests. A helper goal still builds a project model: measure that cost. Sharing across modules may require a compatible reactor batch or a later server-side API; one helper invocation per POM alone does not remove that repetition.

05Product choice · medium effort

Offer a fast editor scope.

For very large management POMs, offer a scan of parent/BOM version declarations, explicit overrides, direct dependencies, and management entries consumed by imported modules.

Keep a full “Audit all declared management entries” action for library/platform maintainers. Track coverage: a fast scan is complete for its stated scope, not for the whole management list.

Payoff: fewer lookups when hundreds of local managed entries are unused by this reactor.
Tradeoff: a published BOM can have external consumers. Keep full scanning as the existing default until the user chooses otherwise.
Preserve the useful detail

Include active-profile declarations and inherited property consumers. If consumer detection is uncertain, include the entry. Separate the “used here” scope from vulnerability/transitive analysis, which is outside the current checker scope.

06Spring Boot option · medium effort

Make the platform update arrive first.

Detect Boot parent/BOM ownership and let a platform-focused view query that declaration before individual managed libraries. Query explicit overrides next; expand library-level findings on request or in the full audit.

A project may care most about one Boot upgrade. Spring documents that each Boot release is tested against a particular dependency set, so separate library bumps deserve their own review. Spring Boot documentation.

Payoff: faster first useful answer; fewer lookups only if the user selects the narrower scope.
Tradeoff: this changes presentation/coverage. A newer Boot version is not proof that every library has the newest version or that the upgrade is compatible.
Parents of parents

A child can inherit Boot through a corporate or reactor parent. Locate the actual owner of the platform declaration and show that source. Do not suggest bumping a reactor parent to an unrelated published release; preserve the current reactor-parent exclusion and guarded fixes.

07Controlled experiment · medium effort

Overlap independent metadata work.

After deduplicating lookups, test a bounded worker pool for independent artifacts. Keep host-level limits and a slot for the selected file; slow background work should not occupy every worker.

Try two workers first, then four. Keep the current serialization for embedders until concurrency is proven safe. Resolver already has metadata threading; the documented aether.metadataResolver.threads default is four. Resolver configuration.

Payoff: latency overlap when repositories are the dominant wait.
Constraint: request granularity matters. Internal threads do not guarantee that separate artifact calls overlap; more threads can worsen throttling and lock contention.
Where to apply it

Prefer bounded batching within the native metadata helper to indiscriminately running POM goals in parallel. Verify which Resolver version IDEA's chosen Maven actually uses and how session properties reach it. Stop increasing concurrency when p95, rate limits, CPU, or cancellation behavior worsens.

08Targeted follow-up · medium/large effort

Collapse plugin branch passes.

The current Patch/Minor path runs display-plugin-updates for each distinct version branch, while each invocation can inspect a broad plugin set.

Fetch plugin version histories once and choose the eligible branch locally. Reuse prerequisite information for candidate plugin releases so a faster path still rejects versions requiring newer Maven.

Payoff: removes repeated full-plugin passes in POMs with many branch prefixes.
Constraint: merely unioning branch ignore rules loses the relationship between a plugin and its allowed branch.
Fallback and evidence

Retain the current native goal for unsupported cases. Measure candidate-POM reads separately from version metadata, because prerequisite checking may still require them. The native goal explicitly accounts for Maven prerequisites; see MojoHaus plugin update documentation.

03 / bold direction

A version index beside the project model.

Maven continues to establish the resolution context. A dedicated lookup layer shares repository facts. The existing snapshot and edit machinery remains responsible for matching results to declarations and validating edits.

1 → Capture

Declarations & ownersLocal and inherited baselines, active profiles, controlling properties, strict edit fingerprints.

2 → Group

Resolution contextsEffective dependency/plugin repos, mirrors, auth/proxy digest, runtime and configuration.

3 → Resolve

Unique version indexesNative metadata batches, shared requests, bounded cache, one fresh generation.

4 → Publish

Per-declaration answersBaseline/mode selection, stable versions, prerequisite checks, incremental results and guarded edits.
Illustrative workload10,000 references

100 modules × 100 overlapping declarations. The present execution unit is the POM, with category and plugin-branch goal passes.

Desired lookup unit400 indexes

If those references map to 400 unique coordinate/context pairs, share 400 version indexes across all consumers and modes.

These are invented workload counts, not observed HTTP counts or a 25× speed claim. Each context may contact several repositories; models, plugin prerequisites, retries and transport behavior add work. Measure the real request reduction.

An even bolder option: persist the index between IDE sessions

Store bounded repository metadata locally with fetch timestamps and a resolution-context digest. Show its age immediately after opening a project; refresh asynchronously when online. Expired results can inform a labelled historical hint, but must not authorize edits or claim a complete fresh check. This helps repeated project opens; it does not improve the first-ever remote lookup. Keep private metadata local and invalidate on configuration changes.

04 / validation

Prove less work before promising faster checks.

The repository already has stage tracing and scaling fixtures. Existing warm editor measurements and local preparation benchmarks do not establish cold, large-project Maven-server performance.

05 / suggested order

Start with duplicate freshness. Aim for the native batch.

  1. Baseline the actual complaint. Trace a Boot child, a huge management POM, and an overlapping reactor. Add coordinate/branch/context counts and repository HTTP counters.
  2. Remove repeated refresh within a scan. Introduce scan generations and successful-revalidation tracking. Prototype short-lived session reuse if setup dominates.
  3. Build the native metadata batch if lookup or goal repetition dominates. First dependencies/parents, then a bounded shared version index and local mode selection. Compare against the existing native path.
  4. Address plugins and tail latency. Add prerequisite-aware plugin histories; test bounded metadata concurrency and failure isolation.
  5. Offer faster scopes as explicit product choices. Used-here management scans and Boot-platform priority can improve perceived speed, with visible coverage and access to the full audit.

My preferred end state: opening a POM usually reuses a fresh version index; Refresh performs one deduplicated native scan; the first useful batch arrives while the rest continues.
