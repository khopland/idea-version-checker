01 / Recommendation

Fix edit validity before expanding coverage.

The strongest part of the project is its respect for native build semantics: IDEA inspections, repository configuration, shared-version ownership, freshness leases, and one-command undo. The next step is to close concrete gaps in those guarantees, then turn the existing checker into a dependency maintenance workflow.

Two release priorities

Prevent npm override conflicts, and include Gradle executable build logic in update validation. Both problems can affect what happens after a user accepts a proposed update. Repair the failing cancellation test in the same release so this behavior is continuously checked.

P1 = fix before the next release. P2 = correctness, robustness, or coverage work for the next maintenance cycle. P3 = uncommon edge case. Priorities are review judgments, not proof of frequency.

Preserve what works

  • Keep Maven, npm and Gradle version ordering ecosystem-specific.
  • Keep provider configuration and credential handling in native tooling.
  • Keep freshness authorization separate from retained editor hints.
  • Keep conservative shared-owner checks and one undoable update command.
  • Keep cancellation, plugin unload, cache budgets, and failed-vs-empty result tests.

Change the next emphasis

Show users why a declaration is skipped, why a target was chosen, which consumers will change, and what remains after editing.

Measure less visible work as carefully as query speed: repeated discovery, input hashing, IDE refreshes, lockfile synchronization, and the cost of a failed review.

Build one tested route from a candidate to an authorized edit. Local fixes, workspace fixes and bulk previews should share its eligibility decisions.

02 / Verified problems

Findings with reproducible triggers

Each item identifies a specific behavior, evidence, a proposed correction, and an acceptance test. Six temporary observation probes passed because they assert the existing defects; the failing repository test is a separate finding.

F1 · P1

An npm update can produce an invalid override

A valid manifest declares dependencies.alpha = "1.2.3" and overrides.alpha = "1.2.3". Updating the dependency to 1.2.9 leaves the override at 1.2.3. npm rejects the result with EOVERRIDE.

Why it happens

The adapter prepares edits from dependency sections only. Neither local fixes nor workspace fixes account for matching direct overrides. The existing npm adapter test even asserts that overrides remain unchanged.

Evidence

Probe testNpmUpdateLeavesDirectOverrideIncompatible applies the current plan and confirms the conflicting values. A separate npm 10.9.8 command returns Override for alpha@1.2.9 conflicts with direct dependency. The unchanged baseline reaches dependency lookup instead of EOVERRIDE.

Proposed change

Before offering an edit, inspect root-level overrides, including object overrides with a "." entry. Initially put affected updates under Needs review. Later offer one explicit grouped edit for the dependency and matching override; preserve $alpha references.

Done when

Valid direct overrides, nested object overrides, aliases, root overrides affecting workspace members, and $ references all remain installable after a selected update. Apply the same guard to local, workspace, and bulk updates.

F2 · P1

Gradle edit guards miss executable build logic

Prepare an update, then change buildSrc/src/main/kotlin/RepositoryPolicy.kt. The old snapshot still passes freshness validation and the old plan applies. Build logic can change repositories, dependency substitution, attributes, and version policy.

Why it happens

Input discovery includes Gradle scripts, TOML, selected configuration files and locks. It omits Kotlin/Java buildSrc sources and their resources. Unlinked sibling included builds and externally applied inputs also require an explicit policy rather than a filename assumption.

Evidence

Probe testGradleBuildLogicEditsRemainCurrentAndApply confirms the Kotlin source is absent from the fingerprint, changes and saves its document, observes isCurrentInBackground == true, and applies the held plan. This reproduces the guard failure with a synthetic candidate; it does not claim a native end-to-end policy exploit.

Proposed change

Track the source/resource inputs of buildSrc and imported included build logic. Reuse one captured input inventory for save, fingerprint, background validation, and pre-edit disk validation. If input coverage cannot be established, present the result as limited and require a fresh validated review before editing.

Done when

Changing or adding buildSrc Kotlin, Java, or resources invalidates held fixes and previews. Add a native fixture where build logic actually rejects the formerly allowed target. Cover included builds, external scripts, and unsaved build logic without fingerprinting every application source file.

F3 · P2

The default test suite fails before testing disable/resume

The current checkout fails BuildCoordinatorTest.testDisablingDuringInspectionDiscardsLateResultAndAllowsResume with NoSuchElementException.

Why it happens

The test locates a checkbox by the old phrase “Check for newer dependency”. Settings now labels it “Enable version checks”. The failure occurs during UI lookup, before the cancellation assertions.

Evidence

The default run completes 503 tests with one failure. A focused second run reproduces the same failure. This is deterministic label coupling, not evidence of a cancellation bug.

Proposed change

Identify the enabled checkbox by a stable component name or a narrowly scoped test accessor. Update this test and avoid searching presentation text for behavior tests.

Done when

The isolated test reaches disable, late completion, and resume assertions. The full default suite passes after the fix; changing visible wording no longer breaks behavior tests.

F4 · P2

A bad catalog field aborts parsing of good siblings

In a catalog containing alpha = { module = 123, version = "1.2.3" } and a valid beta declaration, parsing throws instead of returning a review outcome for alpha and continuing with beta.

Why it happens

Syntax errors are handled, but typed TOML getters such as getString("module") can throw TomlInvalidTypeException. Catalog parsing is also used by inspection fingerprint normalization, so this can suppress more than one row while the user edits a file.

Evidence

Probe testMalformedTypedCatalogThrowsInsteadOfSkipping confirms the exception on syntactically valid TOML with an invalid Gradle field type.

Proposed change

Use safe typed access per entry, validate the schema, and carry a parse diagnostic with an anchor. Catch only expected type/schema failures at that boundary; preserve cancellation and unexpected failures.

Done when

One malformed entry becomes Needs review; valid siblings still produce declarations. Cover bad libraries/versions/plugins table types and bad module/group/name/version.ref values. Never authorize edits to malformed entries.

F5 · P2

Folder exclusions are applied above project ownership

An independent npm project under a directory named build, dist, or vendor is rejected because any ancestor has that name. Gradle uses the same whole-ancestor exclusion pattern.

Why it happens

npm walks parents to the filesystem root. Gradle checks all ancestors before determining whether the file belongs to a linked build. Generated-output heuristics can therefore hide a legitimate project because of its enclosing location.

Evidence

Probe testNpmProjectInsideDirectoryNamedBuildIsExcluded confirms the npm rejection. The Gradle equivalent is supported by the same ancestor predicate in source, rather than a separate native probe.

Proposed change

Determine the content/workspace or linked build root first. Apply generated-directory exclusions relative to that root, and distinguish a selected project root from generated descendants. Keep node_modules and generated child directories excluded.

Done when

A project whose enclosing directory or root is named build remains checkable. Genuine generated manifests under the project remain excluded. Test symlinks, nested independent projects, and explicit current-file actions.

F6 · P2

Classifier declarations disappear from Gradle coverage

A literal Gradle dependency implementation "g:a:1.2.3:tests" produces no declaration at all. It does not appear in skipped coverage or Needs review.

Why it happens

The script parser accepts only coordinates split into exactly three pieces. More complex notations are discarded before the adapter can explain why they cannot be updated.

Evidence

Probe testGradleClassifierNotationVanishesFromCoverage returns an empty declaration list for this recognized dependency call. The gap is observability; no unsafe classifier edit was reproduced.

Proposed change

Separate recognition from automatic edit eligibility. Record a declaration with a manual-review reason for classifier and extension notations. Extend this approach to map notation and other unsupported dependency forms without guessing how to edit them.

Done when

Recognized unsupported calls contribute to skipped/review counts and identify their source. Automatic updates remain limited to forms validated by native ownership and resolution.

F7 · P3

Large Gradle numeric versions receive the wrong severity

2147483648.1.0 → 2147483649.1.0 is newer, but classified as PATCH instead of MAJOR. It can consequently use the wrong configured inspection severity.

Why it happens

Ordering uses BigInteger, while classification uses toIntOrNull() ?: 0. Overflow silently turns both major components into zero.

Evidence

Probe testGradleHugeMajorIsMisclassifiedAsPatch confirms the mismatch. This is an uncommon numeric edge case; it does not bypass the native Patch-mode filter.

Proposed change

Parse numeric components once into a consistent Gradle version value and use it for comparison and change kind. Precompile the constant regular expressions. Keep Maven and npm semantics separate.

Done when

Classification agrees with ordering for large components, omitted components, and supported qualifiers. Existing service-pack and channel behavior remains unchanged.

Small cleanups worth doing

  • Parse Gradle numeric components once; precompile constant regexes.
  • Separate persistent settings data from the Swing configurable, and test controls by stable identity.
  • Replace nested nullable callback state in preview orchestration with explicit Loading, Ready, Applying and Failed states.
  • Group test-only Gradle flags behind a documented configuration object; the aggregation prototype is currently disabled by a system property.

Avoid expensive cleanup traps

Do not replace native resolution with generic registry HTTP calls to reduce line count. Do not collapse all caches into one generic cache immediately. Do not remove scoped result identities, disk checks, or shared-property rules as “complexity”.

Keep pure version selection and report models independent of PSI where practical. A full standalone engine becomes worthwhile when there is a concrete second client.

A possible future review

“Update the platform, synchronize the lockfile, and verify.” The review explains affected modules, blocks conflicting overrides, presents declaration and lockfile diffs, invokes only the selected follow-up operation, and records what passed or still needs attention.

Native verification can fail after an edit. Represent Edited, Synchronized and Verified separately, and retain a recoverable diff. Never present an applied declaration as a validated build.

Small releases with measurable gates

Suggested effort: 2–3 weeks for a focused first slice

Gate: a user can move from hint to reviewed edit to synchronized project, and can identify the failing step without reading logs.

4Expand with evidence

Choose one investment; size it after a prototype

Pick team policy and grouped updates first for teams, broader Gradle/npm manager support for reach, or resolved security enrichment for risk prioritization. Validate demand before a headless engine.

Gate: each new declaration/manager has native configuration, offline, cancellation, scope and update tests. No release based solely on parser unit tests.

Effort is an initial planning estimate for one engineer, not a delivery commitment. Included-build discovery and lockfile workflow design are the largest uncertainties.

Measure success

  • Edit correctness: no offered update introduces a known direct override conflict; changed build logic invalidates a held edit.
  • Coverage: recognized unsupported declarations receive a reason and source location; coverage never grows by silently dropping rows.
  • Responsiveness: compare cached editor hints, first useful result, preview ready, apply and follow-up completion under the same project scope.
  • Native work: retain request counts, cancellation behavior and cache reuse; report cold and warm measurements separately.
  • User completion: track successful synchronization/verification in local test scenarios before adding telemetry or claiming productivity gains.
