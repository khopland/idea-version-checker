04Engineering for a responsive IDE

Remove repeated work before adding concurrency.

First · Gradle scan

One build evaluation, many answers.

Aggregate declaration requests for a linked root. Build ownership/context indexes once, resolve compatible probes once, and fan results back to source files. Retain exact owner agreement for catalog edits.

Success: a multi-module scan uses native invocations by build/batch rather than by file. Same candidates, reasons and repository request semantics on the authenticated fixtures. Mode changes reuse facts only where equivalent Gradle selection can be proved.

Second · Bulk apply

One commit per changed document.

Prepare a document transaction with original text, validated ranges and final replacement text. Complete all cross-file guards before the first write. Keep file-type-specific handling for XML/JSON where direct PSI edits remain safer.

Success: dense Gradle changes commit each document once, preserve formatting/comments, reject stale inputs and undo together. Profile before claiming an elapsed-time gain.

Third · Local hot paths

Separate disk work from model locks.

Keep PSI discovery small, retain immutable declaration indexes by relevant stamps, and move external configuration reads to cancellable background preparation. A user source edit should not hash every credential/init file again.

Correctness constraint: never authorize an edit from a watcher alone. Take fresh fingerprints before apply, including external changes and unsaved documents. Scope validation to the actual shared-consumer graph when that graph is proven complete.

Fourth · Scheduling

Bound work across the whole project.

Preserve interactive/selected-file priority and cooperative Maven handoff. Add queue age, repository cooldowns, bounded pending work and configurable limits for native queries. Publish partial Gradle results once batching exists.

Keep native Maven/Gradle serialization until profiling and platform guarantees justify a change. A cancelled last consumer must terminate its native worker; retries need backoff and must not flood a failing registry.

A measured warning sign: this review's Gradle scaling fixture took 468 ms to apply 100 edits across 100 files; npm took 439 ms in its 101-manifest fixture. These are single headless observations, not native latency percentiles, and the Gradle case does not apply all 10,000 declarations. They justify measuring the write path, especially dense files; they do not establish a production freeze. [S11]

Proposed budgets, not claimed performance.

Record host hardware, IDE/JBR/native runtime, archive hash, project shape and cold/warm state. Use at least 100 completed interactions per latency claim; report incomplete/cancelled interactions separately. Keep request counts and native setup apart from visible latency.

05A rebuild with clear seams

Make facts, decisions and edits distinct.

The existing adapter/core separation is a good starting point. Extend it so scheduling, coverage, freshness and presentation follow one model while each provider keeps its own version and repository semantics. Avoid turning Maven's qualifier ordering or Gradle's variant selection into generic SemVer.

01 · Discover

Immutable declarations

Source ownership, selector, baseline, shared consumers and tracked input stamps.

02 · Query

Native provider facts

Context-keyed metadata/probes with original age, deadline, provenance and failures.

03 · Decide

Policy + coverage

Candidate selection, ignores, runtime constraints, checked/skipped totals and review reasons.

04 · Apply

Validated transaction

Candidate leases, expected text, shared-consumer agreement, one command and undo.

A provider-neutral core

Introduce typed concepts for ResolutionContext, Coverage, CheckState, FailureReason, CandidateLease and EditTransaction. One presentation selector feeds editor hints, status, preview counts and failure summaries. Keep raw provider facts independent of ignore/severity policy.

Make stable declaration identity distinct from character offsets. PSI pointers/ranges belong to prepared edits; cacheable provider facts should contain no live PSI or UI objects. Give every retained map a documented bound and disposal owner.

Native bridges at the edges

Separate Gradle init-script generation and protocol parsing from the IDE task bridge. Treat Maven helper installation, protocol, prerequisites and fallback as a replaceable bridge. Keep npm CLI runtime/configuration resolution isolated from selector logic.

The core coordinator should not unconditionally depend on optional provider classes. Current shared refresh/preview paths call withMavenScanSession; provider-disabled packaged smoke tests should verify that this remains safe before moving ownership into the Maven adapter.

A state machine for review

Replace implicit combinations of running flags, nullable results and closed/reopened dialogs with explicit states: preparing, checking, partially ready, ready, stale, failed, applying and disposed. Coverage is a property of the result, not a tooltip-only string.

Keep preparation cancellable, presentation read-only, and write authorization explicit. A partial check can render useful results but cannot authorize a full audit or a shared edit with unchecked consumers.

A migration that can be compared

Move one seam at a time: presentation model, transaction engine, Gradle aggregation, then coordinator simplification. Run old/new candidate and skip-reason comparisons in fixtures. Use development flags for resolver experiments; never double remote traffic by default.

Preserve settings, plugin ID, inspection IDs, action IDs, ignored releases and dynamic unload behavior. Any settings/storage change needs a migration and rollback plan. Choose 2.0 only when the public behavior or format warrants it.

When a full rewrite becomes reasonable

A full rewrite is reasonable if a prototype demonstrably meets the UX/performance budgets, its provider boundaries are smaller and easier to test, and it passes the existing semantic fixtures plus the missing native matrix. Require byte-for-byte declaration edits where appropriate, equivalent candidate/review results, stable settings migration, current/minimum IDEA support, native authentication/offline behavior and unload/cancellation parity.

Do not make a framework switch the goal. Native Swing/IntelliJ controls already fit the product and platform; a web UI would add focus, theme, accessibility and lifecycle obligations. A pure Kotlin core with thin native presentation and tool bridges is the first design to evaluate.

Clear review intent

Show package, file, change kind and affected consumers. A shared property/catalog row represents one atomic edit and opens a consumer list. Show the actual source owner for parent/platform updates.

Persist filter, focus, selected identities and scroll during a mode/scope refresh. Maintain the existing explicit hidden-selection count. Preserve deselections; if a target changes, mark it for review rather than silently selecting it.

Useful empty and partial states

Use distinct states for “all 24 supported declarations checked; no newer versions,” “8 declarations need review,” “waiting for saved build inputs,” “not imported,” “runtime missing,” “offline cached results,” and “3 packages failed.” Show narrow Maven platform/fast coverage prominently.

Allow recovery in the window. An optional future partial preview may offer independent successful edits only with explicit scope acknowledgement and complete guards for their shared consumers; failed full audits must remain failed.

Calmer settings

Use General, Update policy, Notifications and Advanced groups. Explain the effect of Maven fast checks and persistent metadata where they are configured. Validate malformed ignore/deprecation rows with line-specific feedback.

Offer severity presets and per-ecosystem automatic checks. Keep background checking separate from explicit review actions. Leave periodic remote checks opt-in. Avoid presenting patch/minor labels as compatibility guarantees, especially for 0.x packages.

Finish the update

After a declaration edit, show the changed files and an actionable next step: Maven reimport, Gradle reload/lock review, or npm lockfile synchronization. Use native IDE actions where available and show a command preview before introducing a mutating package-manager action.

Add release-note/changelog links with explicit provenance, a diff, source navigation and optional build validation. Label available versions separately from installed/locked versions. “Newest published” and npm's “latest” tag should be distinct policies.

Accessibility and interaction acceptance

Verify keyboard-only review from editor to filter, scope, policy, table, details and Apply; Tab exits the table, Space toggles selected rows, Escape dismisses the intended popup/window, and Enter never reaches the source editor accidentally. Keep focus stable during asynchronous updates. Confirm screen-reader names and announcements for progress, coverage, changed target and rejection. Check dark/high-contrast themes, 200% UI scale, narrow windows, long coordinates and localized IDEs. Put user-facing strings into a resource bundle before localization expands.

09A staged delivery plan

Put the ambition in a workable order.

Rough effort ranges below assume one experienced maintainer and are planning estimates, not deadlines. Native tooling access, unresolved bugs and fixture setup can dominate the schedule.

Release preparation · 1–2 days

Freeze the candidate and repair the small gaps.

Choose the next version, finalize notes, fix ignored counts and missing links, capture the release ledger, and add the current IDEA verifier target. Define supported scope and candidate freshness. Review current CI on the exact commit.

Exit: correct ZIP identity/notes, existing automated checks green, small presentation regressions covered. No Marketplace publish yet.

Native release evidence · 3–7 days, after usable tooling

Close the stable gates.

Unblock native npm with authorized support, resolve Gradle 2025.3 diagnostics, run current-IDE and provider-disabled smoke tests, then exercise representative large/shared edits and typing. Record archive hashes, profiler evidence, failures and incomplete samples.

Exit: R1–R7 pass for advertised scope, or an EAP-only candidate with explicit remaining gaps. Fix demonstrated stalls before stable; estimates exclude waiting for external tooling access.

First performance iteration · 1–3 weeks

Batch writes and prototype a Gradle build scan.

Implement document transactions, index Gradle ownership, aggregate by linked build, preserve native resolution semantics and collect work/latency comparisons. Move expensive input preparation off EDT and bound result bookkeeping.

Exit: same candidates/skip reasons and edit guards; fewer setups/commits; measured improvement in the named workloads. Keep prototype aggregation behind a development/EAP switch until parity holds.

Review experience · 1–2 weeks

Build one coherent review model.

Introduce typed coverage/failures, filtered status selectors, persistent review intent, structured Needs review, source navigation and file diffs. Simplify menu entry points and settings. Add actionable synchronization guidance and native keyboard/accessibility checks.

Exit: users can explain what was checked, what one selected edit affects, and what to do afterward. Existing Alt+Enter flow remains fast.

Core consolidation · 2–4 weeks as needed

Extract the proven seams.

Separate provider bridges, state machine, candidate authorization and edit transactions. Move optional-provider scan ownership out of shared core, add settings migration where needed, and broaden cancellation/soak/OS validation.

Exit: fewer cross-provider dependencies, bounded ownership, simpler reproducible tests and unchanged behavior. Reassess a full rewrite against actual prototype evidence.

Product expansion · ongoing

Choose the next ecosystem or decision aid.

Prioritize from real user requests: Gradle plugins/custom catalogs, another JavaScript manager, runtime constraints, team policy or optional sync. Build one capability completely with documentation, authentication, native UX and edit safety before adding the next.

Exit per feature: declared scope, meaningful validation and a clear explanation of candidate provenance. Promote from EAP once its gates pass.

If only one larger improvement fits

Choose Gradle scan aggregation plus document batching. It addresses repeated native setup and the least-measured expensive write path, while the existing metadata semantics and safety fixtures provide a strong comparison baseline.

If profiling reveals a different dominant cost, follow that evidence. First-use/cold latency, first useful result, total scan time and warm review speed are separate outcomes.

10Concrete release checklist

From reviewed code to a new version.

  1. Prepare the version. Use a new version such as 1.3.0-rc.1; move the selected Unreleased changes into a dated entry. Keep notes concise and user-focused. Confirm the packaged descriptor carries that version and those notes.
  2. Complete the fixes and native gates. Track R1–R7 by commit/ZIP hash. Resolve blocked advertised workflows before stable; publish an EAP only with clearly stated scope and remaining validation.
  3. Rebuild and verify the finalized candidate. Run the native flags, Python checks, configuration verification and minimum/current IDE verifier targets. Ensure required CI jobs pass on the final commit, not only an earlier green commit.
  4. Install the selected ZIP from disk. Verify upgrade from 1.2.0 retains settings, ignores, inspection configuration and scheduled-check preferences. Exercise review/apply/undo and plugin unload with the selected package.
  5. Review release delivery configuration. Confirm Marketplace token/channel, signing policy and recovery procedure with the release owner. Signing is already supported optionally; verify a signature when enabled. Compare the selected ZIP/checksum to the archive attached and uploaded.
  6. Publish the EAP draft through the established human flow. The existing workflow uses the eap channel for semantic prereleases. Do not move tags or relabel an existing prerelease as the stable upload. Publishing was not authorized or performed by this audit.
  7. Promote with a new stable version. After gates and EAP feedback pass, prepare 1.3.0 and its dated entry. Repeat tagged validation/delivery. Record the final Marketplace/GitHub asset identity.
  8. Check the installed release and recovery path. Verify Marketplace install/update, support links and known limits. For failed delivery, follow the documented asset-only versus Marketplace retry procedure; use a new version for source fixes.
