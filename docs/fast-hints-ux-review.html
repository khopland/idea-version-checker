My recommendation

Optimize the path from opening a file to applying one update.

The implementation removes repeated inspection work, shortens the selected editor’s highlighting batch, prioritizes interactive checks, and opens selectable previews from valid cached results. npm packages and Maven categories now publish finished hints while other queries continue. npm also shares parsed version histories and equivalent workspace actions across consumers, avoiding repeated local sorting and edit preparation. A passive current-file status explains waiting, blocked and failed checks and opens Refresh or Review directly. Repository checks, shared-version safety and undo remain native.

All 315 tests passed, including native Maven, npm and Gradle integration and packaged-plugin unload/reload checks. Authenticated native fixtures confirm early inspection diagnostics while other work is deliberately blocked. Both supported IDEA versions passed compatibility verification. Actual time to a visible hint still needs an end-to-end editor measurement.

Prioritized code review

The findings that guided implementation

The observations below describe the original 4f27b42 baseline. See Delivered changes above for current behavior. Findings 01–03, 05, 06 and 09 are delivered; the core of 04 and 08 is delivered. Native experiments and real-editor latency measurement remain follow-ups. Effort is relative: small = local change; medium = several connected paths; large = adapter or coordinator redesign.

01
First · small / medium

Refresh the active editor sooner.

Observed: FileProblemRefreshQueue uses a fixed 200 ms window for every file, including the file the user is reading. This intentionally batches completions, but also delays the result-triggered restart.

Change: Give the selected editor a 0–50 ms coalescing window; keep the 200 ms batch for other files. Deduplicate requests and limit restart frequency during bursts. Compare 0, 25 and 50 ms in IDEA before choosing the default.

Verify: Measure accepted-result-to-visible-highlight time and daemon restart count. Retain the existing guarantees for continuous completions and cancellation. A shorter queue alone does not guarantee a faster finished inspection.

Evidence: EditorProblemRefresh.kt:25–45; FileProblemRefreshQueueTest covers batching and cancellation.

02
First · small

Capture the Maven inspection snapshot once.

Observed: forFile() asks separately for updates and relocations. Each bridge call captures a snapshot, including declarations and project fingerprints. When quick fixes are built, a lazy field captures another snapshot.

Change: Return the snapshot and report together from the Maven inspection bridge. Reuse them for diagnostics, relocation notices and quick-fix construction during that inspection pass.

Verify: A pass with both updates and fixes should capture one snapshot. Keep fresh validation when the fix is actually applied; do not reuse the old project inputs across suspended work or a write command.

Evidence: MavenVersionCheckService.kt:14–22, MavenDependencyAnalysis.kt:42–45, 181–187.

03
Delivered and measured

Index candidates and workspace consumers once.

Observed: The Gradle inspection calls singleOrNull over all candidates for each consumer and scans notices repeatedly. With D declarations and C candidates, candidate matching is O(D × C). npm loads workspace declarations once per visitor, but scans that list again for every highlighted dependency to construct workspace edits.

Change: Group Gradle candidates/notices by declaration ID once. Preserve duplicate-ID rejection rather than letting associateBy silently pick a candidate. Group npm consumers by artifact once and build only matching fixes. If construction is still expensive, offer the local fix immediately and defer workspace edit preparation until that action is invoked.

Delivered: Gradle candidate/notice indexing and npm artifact grouping are implemented. npm now also shares one workspace action per artifact and exact target version within each visitor; local edits stay separate. A real visitor fixture with 10,000 workspace declarations and 100 warnings in the selected file reduced complete preparation from 1,512 ms to 68 ms median, with equivalent workspace actions reduced from 100 to one. The first registered problem did not improve, and completed IDEA rendering remains unmeasured. Alias operators, distinct targets, stale siblings, scope exclusions, atomicity and undo are covered.

Verify: Benchmark actual visitors with 10,000 declarations, not only snapshot collection. Check shared Gradle versions, npm aliases, scope boundaries and no-downgrade behavior.

Evidence: NewerGradleDependencyInspection.kt:34–50, NpmBuildSystemAdapter.kt:118–144, npm visitor.

04
Next · medium

Put the active file ahead of background work.

Observed: Both automatic scans and checkNow() hold one mutex per adapter ID. A slow npm manifest or Maven POM can therefore block a different file using the same adapter. Whole-project refresh loops are sequential, and discovery completes before checking starts. Invalidation rejects obsolete output but does not cancel the old scan job.

Change: Add an explicit queue: active-file/manual work first, open editors second, remaining project files last. Deduplicate by context and revision, drop superseded queued work, and track running jobs. Start useful work before all project discovery finishes where the adapter can do this safely. Cancel obsolete work only when no current caller needs it.

Verify: During a large project refresh, switch to a different build file and measure its queue wait. Preserve scheduled-check eligibility and npm’s shared-worker ownership. Start with prioritization; add bounded parallelism only for resolution contexts proven independent.

Evidence: VersionCheckService.kt:44–53, 111–139, 147–174. The npm semaphore helps within a check; it does not bypass this file-level lock.

05
Next · medium / large

Publish useful hints before the slowest query finishes.

Observed: npm waits for all package tasks with awaitAll() before returning a report. Maven collects dependency, plugin and parent results before its adapter returns. The coordinator publishes only that final report. One slow query delays unrelated successful hints; a thrown npm query can abort the aggregate.

Change: Add incremental results per package or Maven category, carrying the snapshot revision and individual freshness deadline. Publish completed candidates in small batches and keep the scan’s pending/failed state separate from “no updates.” Show successful hints while the remaining work continues.

Verify: Delay one registry package or Maven category artificially. Other hints must appear before it finishes. Failed or pending items must never look up to date, and incomplete results must not silently qualify a whole-project apply. Preserve strict edit validation.

Evidence: NpmVersionCheck.kt:23–58, MavenVersionLookup.kt:42–51, coordinator publication.

06
Next · medium

Open a preview without forcing another full check.

Observed: Every bulk preview invalidates adapter metadata and calls checkNow() for every snapshot. Even just-checked dependencies pay for fresh native work. The shared report cache does not include update mode in its key.

Change: Build a preview from current, unexpired results for the requested mode, with “Checked 2 minutes ago” and an explicit “Refresh” action. Introduce mode-aware report caching where necessary. For npm, derive patch/minor/major candidates locally from shared raw metadata. Preserve the earliest metadata expiry.

Guardrail: A cached major candidate cannot stand in for the latest patch candidate. Maven and Gradle need the exact mode’s results or a new query. Retained inspection-only reports cannot authorize edits. Refresh must still force native revalidation; final apply must still reject changed inputs.

Verify: A warm same-mode preview performs no native query. Changing mode still returns the newest allowed candidate; configuration edits invalidate the preview.

Evidence: BulkUpdateService.kt:134–148, VersionResultCache.kt:9–26.

07
Profile first · large

Batch Gradle checks by linked build.

Observed: Each snapshot with supported requests invokes a native Gradle task for the same linked root. Each invocation adds a temporary init script, disables configuration cache/configure-on-demand, and requests dependency refresh. A many-module scan repeats build configuration across files.

Change: Experiment with one request set per linked root and mode, retaining each source file, declaration ID and owning resolution context. Dispatch the resulting reports back to their snapshots. Deduplicate only requests whose repositories, attributes, constraints and substitution behavior are equivalent.

Verify: Compare native invocation count, configuration time, first-hint time and candidate parity on a large Gradle build. Test catalogs with multiple consumers, platform/BOM attributes, substitutions, locks and cancellation. Batching should not force the active editor to wait for every module.

Evidence: GradleVersionLookup.kt:27–60. Existing results are scoped by source file; root batching requires a contract change.

08
Experience · medium

Replace the text-only bulk preview with selectable rows.

Observed: The preview is a read-only text area containing paths, changes, reminders and skipped items. The user applies all proposed declarations together. Entry requires Tools → Update Versions → scope → update mode.

Change: Add “Review updates in this file…” beside existing editor actions and Alt+Enter fixes. Use one preview with scope and mode controls, searchable/selectable rows, short relative paths, update-type labels, affected-file counts, and a separate “Needs review” area. Put install/reload guidance after apply and keep essential shared-impact information beside its row.

Verify: Time a developer selecting two changes in a 100-row preview. Check keyboard navigation, focus, screen-reader names and undo. Recompute the plan after selection: removing a consumer must not make a shared-property edit unsafe.

Evidence: BulkUpdateService.kt:164–176, plugin.xml action groups.

09
Experience · medium

Explain empty, waiting and failed states in place.

Observed: A missing report produces no automatic version hint. Empty, pending and failed checks are not represented as distinct diagnostic states. Background failures create warning balloons per failed file, and several stale quick-fix paths return silently.

Change: Add one compact current-file status: “Checking…”, “Up to date”, “Updates available”, “Offline”, “Save build files to check”, or “Couldn’t check · Retry”. Use a short delay before showing transient loading. Group repeated errors by scan/cause, keep details accessible, and offer “Refresh this file” when a fix is stale.

Verify: Slow/offline/unauthorized fixtures must explain why hints are absent without a balloon per module. Use “Up to date” only for a successful complete check of supported declarations. Quick-fix invalidation must not leave users guessing.

Evidence: VersionCheckService.kt:37–41, 177–197; adapter quick-fix guards; Gradle unsaved-input eligibility.

10
npm delivered · native conditional

Reuse npm version ordering; defer riskier native changes.

Observed: NpmRegistry.eligible() parses, filters and sorts the full version history for each declaration. Shared metadata avoids the network repeat, but repeated consumers can still repeat local sorting.

Change: Cache a parsed, descending stable-version list with each metadata generation, then apply baseline, mode and deprecation rules locally. Count its memory against the existing cache limits. Prioritize this only if long package histories show meaningful CPU cost.

Delivered: A parsed index preserves original spelling and equal-precedence order, shares baseline lookups and scans candidates only until a usable release is found. Parsed records and baseline-map entries count against the existing cache budget. Five alternating samples with 5,000 stable versions and 200 consumers reduced the median local selection workload from 1,579 ms to 5.33 ms across three modes, with complete candidate/notice parity. This excludes npm processes, network requests and completed IDEA rendering. The authenticated 101-manifest fixture checks every mode with one request and skips a deprecated highest release.

Later experiments: Maven plugin branch rules can cause one goal per branch; compatible-module embedder reuse could reduce setup. These are already deferred in the repository. Use representative traces and candidate parity before changing native boundaries. Persistent caches or a long-lived Node worker add freshness/lifecycle costs and should follow demonstrated need.

Evidence: NpmRegistry.kt:153–156, MavenVersionLookup.kt:75–79, release follow-up.

Static design sketch. Controls are labels, not functional buttons.

Single dependency

Hint → Alt+Enter → apply. Keep the target version in the action name. Show the shared destination and affected count when one change controls several dependencies.

Several dependencies

Review in this file → choose rows → apply. Use patch-only as a convenient starting filter while allowing the user to change it in the same preview.

After applying

Keep remaining valid hints available. Offer relevant npm install or Gradle reload actions through existing IDE flows. Show their scope and effects before running them.

Small UX improvements worth adding
  • Shorten tooltip copy to package, update type and version change; keep repository or range explanation in secondary detail.
  • Make local override and parent/shared update choices identify the affected file and consumers before selection.
  • Offer optional “Ignore this version” or artifact suppression through standard inspection mechanisms, without removing other update hints.
  • Consider information-level patch hints as an optional low-noise preset. A patch release is not a guarantee of compatibility; preserve the user’s severity choices.
  • A repeated bulk action currently returns silently while a preview is running. Focus the existing preview or show its progress.
  • Current-file actions call saveAllDocuments(). Consider saving only affected build inputs, or explain when resolution requires saving more files.

A useful performance validation matrix
  • Warm and cold native setup; Maven, npm and Gradle separately; current-file and whole-project scopes.
  • Small projects, 100-module/workspace projects and 10,000 declarations; repeated ordinary source edits and dependency edits.
  • Fast local repositories, realistic remote/private latency, one deliberately slow package, and authentication failure.
  • Switch active editors during a project scan; rapid repeated refreshes; save/reload and changed settings during a check.
  • Literal, shared property, parent-managed, catalog and npm workspace fixes; verify undo, downgrade prevention and stale-edit rejection.
  • Measure dozens of repeated warm interactions, for example ≥ 100, and report sample count, median and p95. Treat cold/setup samples separately.
  • Retain traces with fixed stage names and anonymous interaction IDs. Do not add paths, credentials, registry URLs or command arguments.
